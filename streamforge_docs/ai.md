# StreamForge — AI / ML Integration Strategy

**Status:** Future-facing specification · **MVP policy:** No AI/ML dependency.

## 1. Purpose

The project is a Data Engineering platform first. AI is not required to prove event ingestion, streaming, data quality, storage, orchestration, or analytics. Do not add an LLM merely to make the project appear more advanced. Reliable and well-measured data foundations come first.

## 2. Potential future use cases

Only consider these after the core pipeline is correct and a sufficiently large, documented synthetic dataset exists:

1. **Anomaly detection:** flag unusual cancellation rates, fare distributions, or event-volume spikes.
2. **Demand forecasting:** forecast ride volume by coarse city/time bucket using historical synthetic data.
3. **Data-quality assistance:** cluster or summarize validation failures for an operator; deterministic rules remain authoritative.
4. **Natural-language analytics (optional):** translate a restricted set of approved questions into predefined metrics. Do not permit arbitrary generated SQL against production data.

## 3. Recommended progression

- Stage 0: no model; establish event quality, lineage, metric definitions, and baseline distributions.
- Stage 1: implement deterministic statistical baselines (rolling averages, quantiles, threshold rules).
- Stage 2: evaluate a simple ML model offline using a time-based train/validation split and documented metrics.
- Stage 3: deploy inference as an isolated optional component with monitoring and a fallback to normal analytics.

## 4. Data and evaluation requirements

- Use synthetic data and document how it was generated; synthetic patterns may not represent real-world behavior.
- Prevent leakage: split chronologically for forecasting and do not use future information in features.
- Compare against a simple baseline; report precision/recall or forecast error as appropriate.
- Record dataset size, time range, feature definitions, random seed, model version, and limitations.
- Monitor drift and false positives; provide a way to disable model-driven alerts.
- Never present model output as guaranteed truth or as an operational decision without human review.

## 5. LLM / natural-language query safety

If an LLM feature is approved later:
- Expose only allowlisted metrics, dimensions, and query templates.
- Prefer parameterized query plans generated by trusted code over free-form SQL execution.
- Enforce read-only database credentials, row/time limits, and query timeouts.
- Treat event payloads and user prompts as untrusted input; do not follow instructions embedded in data.
- Do not send secrets, personal data, or unrestricted raw event payloads to external model providers.
- Log prompt/model/version and query metadata with appropriate redaction; define retention and consent requirements.
- Provide a non-AI fallback and clearly label generated explanations.

## 6. Architecture boundary

Any future model should consume curated data from a documented interface (for example, an analytics table or feature dataset). The current MVP architecture and its approved decisions are recorded in `architecture.md` and `adr/0001-mvp-baseline-decisions.md`; AI/ML remains outside the critical ingestion and persistence path. It must not be inserted into the Kafka consumer's critical persistence path unless a separate ADR demonstrates a compelling need, failure isolation, latency budget, and fallback strategy.

## 7. Approval gate

Before implementation, the owner must approve a short proposal describing the user problem, data availability, baseline, model choice, evaluation plan, privacy/security impact, operational cost, and rollback strategy. Update this document and architecture ADRs before coding.
